# AI 계획: 사건 조회와 원인 설명

## 현재 구현

- 채팅은 Reflector → Action Planner → Executor 흐름이다. Executor는 별칭 확인, 설비 현황, 센서 트렌드, 알람 우선순위(`_priority_reply`), 초기 알람 보고서(`_initial_alarm_report_reply`)를 처리한다. `maintenance_report`, `inspection_evidence` 에이전트가 있다.
- 사건 개념이 없어서 "P3 왜 알람 떴어?", "원인이 뭐야?"에 알람 정보만 답할 수 있다.
- 데이터는 [BE 계획](be.md)의 사건 API, 우선순위 응답의 `incident_id`, 알람의 `peak_level`을 사용한다.

## 새 의도와 Tool

| 질문 예 | 의도 | 호출 |
| --- | --- | --- |
| "지금 진행 중인 사건 있어?", "이번 달 CDU 사건" | `incident_list` | `GET /api/incidents?status/from/to/equipment_group_id`, 최대 10건 |
| "P3 무슨 일이야?", "P1 원인 뭐야?" | `incident_detail` | 별칭으로 설비를 확정하고 진행 중이거나 가장 최근 사건의 상세를 조회한다. 여러 건이면 선택지를 보여준다. |
| "이 알람 왜 떴어?" (우선순위 답변 다음) | `incident_cause` | 직전 답변의 대표 알람 `incident_id`로 상세를 조회한다. 없으면 "연결된 사건 없음"이라고 답한다. |
| "조치해야 돼?", "얼마나 급해?" | `incident_cause`(조치 관점) | `actionable`, `alarm_grade`, `grade_reason`, `response_time_h`, `top_pof` |
| "이 사건으로 보고서 써줘" | `maintenance_report` | 사건 상세를 입력으로 초안을 작성한다(아래). |

- Reflector와 Action Planner에 위 의도를 추가한다. 설비 이름은 기존 별칭 조회로 확정한다(`P1`, `1번 펌프`, `P-1`).
- 날짜가 있는 질문은 KST 기준 `as_of`로 넘긴다. 진행 중 여부는 BE `status`를 그대로 쓴다.

## 답변 구성

1. **요약 한 줄**: 설비, 상태(진행 중/종료), 최고 등급, 진단명(추정)
2. **경과**: 시작 → 감지 → 첫 알람 → (예상) 종료, 선행 센서. 예: P3는 11-08 시작, 11-09 감지, 11-19 08:00 토출압 예측 알람, 09:52 임계치 초과.
3. **관련 알람**: 개수, 센서, 유형(예측/임계치 초과). 알람 등급(경고)과 최고 도달 등급(위험)이 다르면 둘을 구분해 말한다("경고 경계에서 판정됐고 구간 중 위험 수준까지 도달").
4. **원인 후보**: rank 순으로 고장명, 점수, `evidence`를 원문 그대로 옮긴다. 1순위는 "진단(추정)"이며 확정 원인처럼 말하지 않는다. 후보가 1개면(P3) 비교 후보가 없다고 밝힌다.
5. **대응**: 대응 등급·사유, 조치 필요 여부, PoF. 구체적 조치는 `inspection_evidence` 근거가 있을 때만 제시한다.
6. **링크**: 사건 상세, 사건 구간 트렌드

- 근거 문장과 BE 응답에 없는 수치는 만들지 않는다.
- 사건 종료를 "알람 해제"로 바꿔 말하지 않는다.
- **우선순위 답변**: BE가 반환한 순서와 CoF를 그대로 쓴다(P1 1.67 → P2 1.0 → P3 1.0 → P4 0.83). P2와 P3가 동점이면 "점수가 같아 먼저 발생한 알람을 앞에 둠"이라고 설명한다. 각 항목에 진단명과 "사건 보기"를 덧붙이고, 사건 점수 순서(P1 → P2 → P4 → P3)를 대응 순위처럼 말하지 않는다.

## 정비 보고서 초안

- 입력: 사건 요약, 후보, 연결 알람, (있다면) 점검 근거
- 매핑: 증상 = 알람 센서·구간·최고 도달 등급과 선행 센서, 의심 원인 = 후보(점수순, 근거 포함), 위험 = 대응 등급·사유·PoF, 조치 = 점검 근거가 있을 때만 쓰고 없으면 "검토 필요"
- 원인과 조치는 확정 전 "검토 항목"으로 남긴다.

## 검증

- "P1 원인 뭐야?" → 캐비테이션(추정, 7.3), 후보 3개, 근거 "흡입압 -28 %…", 관련 알람 4개
- "P3 무슨 일이야?" → 임펠러 마모, 선행 센서 토출압, 첫 알람 11-19 08:00, 후보 1개
- "P5 사건 있어?" → 사건 없음
- 우선순위 질문 → P1 1.67 → P2 1.0 → P3 1.0 → P4 0.83, 동점 설명, 항목마다 진단명과 사건 링크(기존 테스트 기대값 1.60/1.20은 새 값으로 갱신)
- `as_of` 11-18 질문 → P2·P3·P4 진행 중, P1은 아직 시작 전
- 답변의 수치와 근거가 모두 BE 응답에서 나왔는지 추적 가능해야 한다.
