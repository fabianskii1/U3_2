# AI 계획 — 알람 대응 순위와 근거 설명

## 현재 구현

- `alarm_priority` 질문은 Reflector → Action Planner → Executor를 거쳐 BE의 `get_alarm_priorities`를 호출한다. 일반 요청은 설비별 최대 3개를 조회한다. 1순위, 전체 순서, 개별 알람 순위와 두 설비 비교를 지원한다.
- 채팅은 기준 시각(KST), 설비·대표 센서, 등급·유형, CoF, 알람 시작 시각, 이유와 링크를 보여준다. 활성 알람·영향 설비·고유 조건 집계는 BE 응답에서 읽는다.
- 날짜·시각을 지정한 순위는 `as_of`로 재생한다. 후속 센서 트렌드에서 같은 기준 시각을 유지하고, 초기 보고서 요청에는 선택한 알람의 저장본을 조회한다. [BE 구현 및 검증 기록](be.md)
- BE 테스트 21개에서 채팅 순위, 설비 비교 범위, KST 시각과 후속 트렌드, 저장 보고서, 상태별 응답을 확인했다.

## 질문 해석과 Tool 호출

| 질문 | 호출과 범위 |
| --- | --- |
| “지금 알람 뭐부터 봐야 해?” | `group_by=equipment`로 조회한다. 질문에 지정한 설비·공정·플랜트 범위를 우선 적용하고, 대상이 생략되면 화면 또는 이어지는 대화의 검증된 범위를 사용한다. |
| “1순위만 알려줘” | 같은 범위와 정렬을 유지하고 `limit=1`을 전달한다. 일반 조회는 3개까지 표시한다. |
| “전체 순서” 또는 “P1과 P2 비교” | 전체 요청에는 BE 상한 100개를 적용하고 상한에 도달하면 반환 범위를 표시한다. 특정 설비 비교는 DB 별칭으로 대상을 확정한 뒤 두 설비 ID를 같은 순위 서비스 호출에 전달한다. |
| “11월 19일 14시 기준 순위” | 날짜와 시각을 확정해 시간대가 있는 `as_of`를 전달한다. 한국어 현장 시각의 기본 시간대는 KST다. 연도나 시각을 확정할 수 없거나 미래 시각이면 다시 확인한다. |
| “개별 알람 순위” 또는 “P2 알람 이력” | 개별 순위는 명시적 요청에 `group_by=alarm`을 사용한다. 이력은 지정된 설비·기간·유형을 유지해 이력 화면으로 연결하거나, 이력 조회 Tool이 추가되면 해당 서버 필터를 사용한다. |

- 설비명, 설비 유형, 센서와 별칭은 기존 BE 조회로 확인한다. 후보가 여러 개면 질문으로 범위를 확정한다. 조회에 실패하면 실패를 알리고, 빈 순위로 처리하는 흐름을 피한다.
- 현재 순위는 `as_of`를 생략하고, 과거 순위는 지정 시각의 수신·해제 기록을 사용한다. 과거 상태가 확인되지 않으면 서버의 미확인 결과를 전달한다. 조치 완료나 센서 복귀 시각을 근거로 활성 여부를 추정하지 않는다.

## 응답에 사용할 필드

- BE가 반환한 순서와 `rank`를 유지한다. 각 항목은 설비, 대표 센서, 심각도, 발생 유형, `alarm_start_time`, CoF, 서버의 `reason`을 표시한다. 유형이 비어 있는 기존 이력은 미기록으로 표시할 수 있다. CoF는 대응 순위를 설명하는 점수이며 고장 원인은 별도의 근거가 있을 때 설명한다.
- 전체 요약은 `active_count`(활성 알람 행), `affected_equipment_count`(영향 설비), `condition_count`(고유 센서·setpoint 조건)를 구분한다. 설비별 설명은 `equipment_active_count`, `prediction_count`, `threshold_exceeded_count`, 해당 설비의 `condition_count`를 사용한다. 순위 목록이 제한돼도 집계는 서버가 반환한 조회 범위의 값이다.
- `setpoint_id`는 당시 적용된 규칙의 식별자로 표시할 수 있다. 방향·연속 판정 분·계산값은 해당 규칙이나 분석 근거를 실제로 조회한 경우만 제시한다. 예측과 후속 임계치 알람은 센서·setpoint가 같아도 개별 이벤트로 표시하며, 명시적인 연결 근거가 있을 때만 같은 사건으로 설명한다.

| BE 상태 | 답변 기준 |
| --- | --- |
| `ok` | 순위와 기준 시각을 보여준다. `unscored_count`·`unknown_count`가 있으면 각각 미평가·상태 미확인 건수를 덧붙인다. |
| `unscored` | 활성 알람이 있으나 CoF가 평가되지 않아 순위를 제시할 수 없다고 안내한다. |
| `unavailable` | 조회 범위에 이력이 있으나 활성 여부가 확인되지 않았다고 안내한다. |
| `empty` | 확인 가능한 범위에 활성 알람이 0건이라고 안내한다. 설비 정상 여부에는 별도 근거가 필요하다. |
| `no_data` | 지정한 범위와 기준 시각에 해당하는 Setpoint 알람 이력이 없다고 안내한다. |

## 링크, 초기 보고서, 후속 질문

- 각 항목은 실제 `equipment_id`·`sensor_id`·`alarm_id`로 설비 링크를 만든다. 과거 조회의 후속 질문에는 선택한 알람과 기준 시각을 함께 전달한다. 사용자가 다른 설비나 센서를 명시하면 새 대상을 조회한다.
- 초기 보고서 요청에는 선택한 알람 ID와 `has_initial_report`를 확인하고, BE의 저장본 조회 기능을 채팅 Tool에 연결한다. 응답에는 보고서 생성 시점, 연결된 설비·센서·setpoint, 알람 발생 전 7일 추이, 점검 출처를 사용한다. 저장본이 없거나 센서 이력이 부족한 경우 각각 안내한다.
- 초기 보고서와 채팅의 정비 보고서 초안을 구분한다. 후자는 연결된 알람 및 조회한 점검 근거로 작성하고 확정되지 않은 원인과 조치는 검토 항목으로 남긴다.

## 검증 기준

- 원본 CSV만 적재한 경우 2026-11-19 14:00 KST의 대상 알람은 상태 미확인 10건이다. 이 경우 채팅에도 현재 또는 과거 활성 순위를 표시하지 않는다.
- 같은 시각에 활성 근거가 있는 검증용 이벤트를 사용하면 P1 1.60 → P2 1.20 → P3 1.00 → P4 0.83이다. 알람 10건(예측 6·임계치 초과 4), 고유 조건 6개, 영향 설비 4대를 구분한다. P5·P6는 테스트 순위에 없다. BE에서 두 시나리오는 이미 확인했으며, 채팅 연결 후에도 같은 결과를 검증한다.
- 각 상태 문구, 일부 CoF 미평가, 모호한 별칭, 시간대 변환, 조회 실패, 빈 보고서, 후속 질문의 알람 문맥을 테스트한다. 같은 범위·기준 시각에서 대시보드와 채팅의 순위 및 대표 알람 ID가 일치해야 한다.
- 합성 정답지는 검증에 사용한다. 답변의 관측과 판단 근거는 BE 응답, 해당 센서 데이터, 저장 보고서 또는 점검 출처로 추적 가능해야 한다.
