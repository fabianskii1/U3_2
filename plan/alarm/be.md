# BE 계획: 알람 수신, 순위 조회, 초기 보고서

## 적용 및 검증

- 개발 DB의 Alembic `ab27c93e4501` 스키마에서 수신·이력·설비별 우선순위 API를 구현했다. 실제 상태 재생에는 기존 `alarm_intake.response`의 수신 상태와 해제 이벤트를 사용한다. 수신 근거가 없는 알람의 과거 상태는 미확인으로 처리한다. 요청 예시와 응답 필드는 [BE README](../../BE/README.md)와 OpenAPI에 기록했다.
- BE 전체 테스트 15개를 통과했다. 유효 기간 경계, 이력 커서, 순위 동점·미평가, 동시 중복 수신, 해제 전후의 재생과 초기 보고서를 확인했다. 개발 DB에서 CSV 원본 10행은 미확인으로 응답했고, 별도 테스트 수신 10건은 고유 조건 6개와 설비 순위 P1 > P2 > P3 > P4를 재현했다. 재생 검증은 롤백했다.
- 개발 DB의 알람 20행과 플랜트 필터로 이력 쿼리의 실행 계획을 확인했다. PostgreSQL은 알람을 순차 스캔하고 설비 PK 인덱스로 조인했다. 이 검증의 이력 쿼리 실행 시간은 약 0.07ms였으며, 데이터가 늘어난 환경의 성능은 별도 측정이 필요하다.

## 현재 상태와 계약

- 현재 `POST /api/alarms/intake`는 Bearer 토큰으로 Setpoint 이벤트를 받고 `source_event_id`로 멱등 처리한다. 같은 플랜트의 활성·CoF 평가 완료 알람 1순위와 초기 보고서 스냅샷을 저장한다.
- `GET /api/alarms/priorities`는 CoF 내림차순, 심각도 내림차순, 발생 시각 오름차순, 알람 ID 오름차순으로 **알람 행**을 정렬한다. `GET /api/alarms/history`는 이력 페이징을 제공하지만 활성 상태와 CoF를 응답에서 제외한다. 현재 알람 모델과 수신·순위·이력 코드는 `alarm_start_time`을 사용하며 `measured_value`·`threshold_value`를 알람 필드로 요구하지 않는다. 보고서·채팅을 포함한 연계 계약을 최종 점검한다.
- 이번 목표는 동일한 서버 순위를 대시보드와 AI에 제공하고, 제공된 펌프 자료로 검증 가능한 설비별 대응 순서를 만드는 것이다. DB의 원본/상태 의미와 개발 DB 적용 절차는 [DB 계획](db.md)에 따른다. CSV 적재 알람의 `is_active=NULL`은 상태 미확인이며 활성으로 추정하지 않는다.

## 수신·판정 경계

1. 모니터링 분석기가 1분 데이터, 운전 상태, 적용 중인 setpoint를 읽고 알람을 판정한다. `FIXED`, `BASELINE_RATIO`, `BASELINE_OFFSET`, `EXPECTED_OFFSET` 계산과 `filter_minutes` 연속 판정은 분석기 정의를 확인해 구현한다. 참조값 계산 규칙이 없으면 임의 경계를 만들지 않는다. BE 수신 API는 알람 시작 시각·설비/센서/setpoint·유형·등급·CoF를 검증해 저장한다. `measured_value`·`threshold_value`를 요청 필수값이나 `alarm` 저장 필드로 요구하지 않는다.
2. CSV에는 `예측` 6행과 `임계치 초과` 4행이 있고 현재 수신 API는 `Setpoint` 전용이다. API 계약을 두 축으로 분리해 Setpoint **근거/범주**와 예측·임계치 초과 **발생 유형**을 각각 보존한다. 같은 센서·setpoint의 예측과 후속 임계치 이벤트는 별개 원본 알람이며, 대시보드의 영향 설비/조건 집계에서는 중복 제거한다.
3. 수신 시 설비·센서·setpoint 소속과 유효 기간(`effective_to=NULL`이면 계속 유효), 단위, 타임존 있는 `alarm_start_time`, `주의/경고/위험/비상`의 0~4 등급 매핑, 유한 점수, 미래 시각 제한을 확인한다. 동일 `source_event_id`·동일 내용은 저장 응답을 재생하고 내용이 다르면 409를 유지한다. 과거 자료 적재는 실시간 미래 시각 검사와 별도 경로로 다룬다.
4. 해제 이벤트의 `closes_source_event_id`는 실제 활성 알람을 가리켜야 한다. `alarm_end_time`(조치 완료) 또는 `sensor_end_time`(센서 복귀)을 해제 이벤트로 자동 간주하는 정책은 만들지 않는다. 분석기의 실제 해제 판정이 있을 때만 상태를 바꾼다.

## 우선순위 API

- 공장/그룹/설비 필터와 `as_of` 시각을 명확히 한다. 실시간 호출은 서버 현재 시각, 데이터 재생 및 14:00 검증은 지정 시각의 **그때 활성 상태**를 사용한다. 현재 `is_active` 단일 플래그만으로 과거 상태를 재현할 수 없으므로 상태 이벤트 또는 유효 기간을 별도로 설계하고 구현한다. CSV의 조치 완료 시각과 센서 복귀 시각으로 과거·현재 활성 상태를 추정하지 않는다. 정렬·기간 필터·커서에서 `occurred_at` 대신 `alarm_start_time`을 사용한다.
- 화면의 대응 순위는 설비별 활성·평가 완료 알람 중 최고 CoF 한 건을 대표로 선택한다. 같은 설비의 예측·임계치 초과 이벤트 수와 고유 센서·setpoint 조건 수를 구분해 돌려준다. 순위를 중복 설비 행으로 늘리지 않는다. 동점은 대표 알람의 심각도, 발생 시각, 안정적인 ID 순으로 해결한다.
- `status`, `as_of`, `active_count`, `unscored_count`, `unknown_count`, `items`의 의미와 범위를 OpenAPI에 고정한다. 평가되지 않은 활성 알람은 순위에서 제외하되 누락 건수를 표시한다. `is_active=NULL`인 적재 알람은 `unknown_count`에만 포함하고 순위 항목이나 `active_count`에 넣지 않는다. 데이터 없음, 활성 알람 0건, 상태 불명, CoF 미평가를 서로 구분한다.
- 대시보드와 채팅이 동일 서비스/조회 시각/필터를 쓰게 한다. 필요하면 현재 `/api/alarms/priorities`에 설비별 모드를 추가하거나 별도 경로를 두되 기존 알람 행 조회의 사용처를 점검해 호환성을 유지한다.
- 이력 API는 서버 측 기간·플랜트·그룹·설비·심각도·발생 유형 필터와 커서 페이지네이션을 제공한다. 응답에 `alarm_start_time`, 원본 유형, setpoint ID, CoF와 상태를 포함한다. 실측값·계산된 경계값은 `alarm` 응답에서 제거한다. 별도 분석 근거 저장소가 확정되기 전에는 과거 값을 재계산해 필수 필드처럼 내보내지 않는다. FE가 전체 이력을 반복 로드해 브라우저에서만 필터링하지 않도록 한다.

## 초기 보고서와 오류 처리

- 1순위가 확정되면 근거 알람의 설비/센서/setpoint, 유형, CoF, `alarm_start_time`, 최근 7일 추이 요약 및 기존 점검 근거를 묶어 초기 보고서를 저장한다. 알람 테이블에서 실측/기준 숫자를 읽어 문장에 넣지 않는다. 트렌드 데이터 없음/신호 중복 시 그 상태를 명시한다.
- `alarm_intake.response`의 보고서 스냅샷은 수신 시점 결과다. 이후 순위가 바뀌어도 이전 보고서가 다른 알람을 가리키지 않는다. 조회 API는 저장본을 그대로 반환한다.
- 수신 실패 시 알람/영수증/보고서가 부분 저장되지 않도록 트랜잭션을 유지한다. 토큰 누락, 잘못된 ID, 단위 불일치, 중복 이벤트 충돌, 해제 대상 없음, 과도한 기간/limit을 검증한다. 기존 수신·순위·이력·채팅 코드와 테스트의 제거된 컬럼 참조를 모두 바꾼다.

## 완료 기준

- 2026-11-19 14:00 KST 원본 알람 10행을 네 설비·여섯 고유 센서/setpoint 조건으로 집계하고 설비별 최고 점수 P1 1.60 > P2 1.20 > P3 1.00 > P4 0.83을 재현한다. P5·P6는 원본 알람이 0건이다. 활성 상태 근거가 확보된 별도 재생 검증에서는 같은 설비 순위를 확인한다. `is_active=NULL`인 CSV 적재 결과만으로 활성 순위 API의 네 설비 노출을 성공 기준으로 삼지 않는다.
- Setpoint 264행의 참조값·nullable 종료 시각·방향·연속 판정 분 검증, 예측→임계치 이벤트 연결과 중복 집계 방지를 확인한다. `measured_value`·`threshold_value` 없이 수신·순위·초기 보고서가 동작해야 한다.
- P1~P6 1분 자료 교체는 여섯 CSV를 사전 검증하고 두 시계열 테이블의 해당 설비 행만 교체한다. 현재 연간 CSV용 스크립트의 파일 경로·헤더·충돌 거부 로직을 이번 작업에 맞게 변경하거나 전용 임포터를 작성한다. 실패 시 기존 자료가 유지되도록 한다.
- 개발 DB에서는 기존 실측·기준값을 복구할 필요가 있으면 마이그레이션 전에 백업한다. `BE/`에서 `python -m alembic upgrade head` 후 `python -m scripts.import_cdu_alarm_fixture --data ../plan/alarm/data`로 먼저 검증하고, `--apply`를 붙여 적재한다. 마이그레이션 `ab27c93e4501`의 `btree_gist` 의존성과 두 시계열 교체·setpoint·알람 적재 결과를 확인한다. 같은 파일 재실행 시 중복이 없는지, `is_active=NULL`과 상태 불명 응답이 유지되는지 검증한다.
- 평가 점수 누락, 동점, 동시 수신, 해제 및 재수신, 시각 경계, 이력 페이지 분할 테스트를 통과한다.
- OpenAPI 요청/응답 예시, 실제 마이그레이션 의존성, 성능/인덱스 확인 결과를 기록한다.
